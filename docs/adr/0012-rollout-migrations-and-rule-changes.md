# ADR-0012: Rollout, migrations, rollback and permission-rule changes

Status: proposed, 2026-11-03 (added after plan review finding F13). Confidence: medium-high.

## Decision

1. **Migrations are forward-only, expand/contract.** Each release's migrations add columns, tables and policies first (expand), ship code that writes both shapes where needed, then a later release removes the old shape (contract). Downgrading code is supported only to the previous minor release and only while the contract step has not run; this is documented per release.
2. **Hand-written SQL migrations for security-relevant objects.** RLS policies (`USING` and `WITH CHECK`), roles, triggers, `SECURITY DEFINER` functions, pgvector indexes and partitions are plain SQL files under `packages/db/migrations`, reviewed as code; Drizzle (pinned 0.45.x) is used for application tables and queries. The schema lint (ADR-0001) runs after every migration in CI and asserts: every tenant table has `org_id`, `FORCE ROW LEVEL SECURITY`, a policy with both `USING` and `WITH CHECK`, and every trigger or definer function filters by `NEW.org_id`/`OLD.org_id`.
3. **Backup before upgrade.** `docker compose` upgrade docs and the Helm pre-upgrade hook run a logical backup (`pg_dump` of the tenant schema plus an object-storage manifest) before migrations; restore is rehearsed in CI monthly against the previous release's seeded database. Per-org restore from a shared backup is a documented worker job (`org.restore`) that runs under `withTenant` in one transaction as delete-then-insert of that `org_id`'s rows (never a schema swap, which would affect every org). Because an older backup can resurrect revoked memberships, tuples and sessions, the restore keeps the current membership and deactivation state unless an admin explicitly chooses to restore them after review, bumps every `authz_epoch` and `content_epoch` in the org plus the org sequence, and revokes all sessions and refresh tokens for the org. A test restores a backup taken before a revocation and asserts the revoked user still has no access.
4. **Feature flags for new read paths.** New feed, search or retrieval paths ship behind per-org flags defaulting off, with the old path retained for one release.
5. **Permission-rule change procedure.** Any change to the predicates or tuple-writing rules (ADR-0002) requires: an update to the reference implementation; the fixture matrix extended for the new case; a shadow-compare job that evaluates the old and new SQL predicates for a sample of (user, content) pairs on a copy of production-shaped data and reports differences; a release note stating the semantic change; and the new predicate enabled only after the shadow report shows only intended differences.
6. **Embedding model changes** create a new index with its own `embedding_model`/`dims` and re-embed in the background; queries switch when coverage reaches 100% for the org; the old index is dropped after one release.
7. **Release gates.** CI must pass lint, typecheck, unit, integration (Postgres via testcontainers), the fixture matrix, migration-from-previous-release, license and secret scans, SBOM; the click-test suite runs on a compose stack before tagging. Hosted releases go canary cell → all cells with rollback by image tag and the expand/contract rules above.
